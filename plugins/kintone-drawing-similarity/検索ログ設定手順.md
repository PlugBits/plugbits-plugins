# 類似図面検索の使用ログ 設定手順

トライアル利用を「感想」ではなく「回数と採用率」で語れるようにするための機能。
1回の検索 = ログアプリ1レコード。検索実行時にレコードを作成し、結果クリック・
フィードバックで同じレコードを更新する。

**画像は記録しない。図番とスコアだけ。** ログアプリID未設定時は機能全体が無効
（no-op）になり、本体（検索・登録・ギャラリー等）の動作には一切影響しない。

---

## STEP 1: ログアプリを作る

kintone で新規アプリを作成し、以下のフィールドを**フィールドコードを厳密に一致させて**追加する
（フィールドコードが1つでも違うと、そのフィールドだけ黙って保存されない）。

| フィールドコード | 種類 | 備考 |
|---|---|---|
| `search_id` | 文字列（1行） | 検索ごとのUUID |
| `searched_at` | 日時 | 検索実行時刻 |
| `user_code` | 文字列（1行） | 検索したユーザーのログインコード |
| `query_app_id` | 数値 | 検索を実行したkintoneアプリのID |
| `query_record_id` | 数値 | 詳細画面からの検索のみ値が入る（アップロード検索は空） |
| `query_code` | 文字列（1行） | 検索元の図番。アップロード検索は空 |
| `result_count` | 数値 | 返ってきた候補の総数 |
| `top_score` | 数値 | 1位のスコア（0件なら0） |
| `results` | 文字列（複数行） | 上位10件の `{code, recordId, score, rank, docType}` のJSON配列 |
| `elapsed_ms` | 数値 | `/similar` 呼び出し〜応答受領までのミリ秒 |
| `clicked_code` | 文字列（1行） | 最初にクリックされた結果の図番（未クリックなら空） |
| `clicked_rank` | 数値 | 最初にクリックされた結果の表示順位（1始まり） |
| `clicked_at` | 日時 | 最初にクリックされた時刻 |
| `feedback` | ドロップダウン | 選択肢: `未回答` / `役に立った` / `役に立たなかった`。初期値 `未回答` |

`results` は候補一覧のJSON文字列であり、画像・ファイル本体は一切含まれない。

## STEP 2: アクセス権を設定する（重要）

**このアプリを使う全利用者に「レコードの追加」「レコードの編集」権限を付与すること。**

- 追加権限が無い → 検索してもログレコードが作られない（`console.warn('[SearchLog]', ...)` が
  出るだけで、検索自体は普通に動く＝気づきにくい）。
- 編集権限が無い → クリック・フィードバックが記録されない。
- **これを忘れると、エラー画面もアラートも出ないまま、ログだけが黙って全部失敗する。**
  トライアル終了後に「ログが1件もない」と気づくのが一番痛いので、STEP 5 の確認手順を
  必ず導入直後に行うこと。

## STEP 3: プラグイン設定でログアプリIDを指定する

対象アプリのプラグイン設定を開き、「利用ログ」カードの **検索ログアプリID** に
STEP 1 で作ったアプリのアプリID（数値）を入力して保存する。空欄のままなら機能は無効。

## STEP 4: 推奨の一覧・グラフ

ログアプリ側に以下を作っておくと状況把握が早い。

- **一覧**: `searched_at` の降順（最新の検索が上）。
- **グラフ（日別検索件数）**: 種類=棒グラフ、集計方法=件数、横軸=`searched_at`（日単位）。
  稼働日ごとの利用ペースが一目でわかる。
- **グラフ（採用順位の分布）**: 種類=棒グラフ、集計方法=件数、横軸=`clicked_rank`。
  1位以外がよく開かれているなら、スコアリングの見直し材料になる。

## STEP 5: 動作確認チェックリスト

導入直後に**必ず**この順で確認する。④⑤は本番運用で特に重要（絶対条件そのもの）。

- [ ] ① プラグイン設定でログアプリIDを設定し、保存した
- [ ] ② 詳細画面またはアップロードで類似検索を実行 → ログアプリのレコードが1件増える
      （`search_id`・`searched_at`・`user_code`・`results` 等が入っている）
- [ ] ③ 検索結果のカード（またはアーカイブ結果のGoogle Driveリンク）をクリック →
      同じレコードの `clicked_code`・`clicked_rank`・`clicked_at` が埋まる（2回目以降クリックしても
      上書きされないことも確認）
- [ ] ④ **プラグイン設定のログアプリIDを空にする** → 検索・結果表示・登録が今までどおり
      動くこと（フィードバックUIも表示されなくなること）
- [ ] ⑤ **ログアプリのアクセス権を一時的に外す（または存在しないアプリIDを指定する）** →
      検索・結果表示・登録が今までどおり動くこと（ブラウザのコンソールに
      `[SearchLog] ...` という警告が出るだけで、ユーザーには何も表示されないこと）

④・⑤ は「ログの失敗が本体に一切影響しない」ことの確認であり、これが崩れていたら
即座に直す（本体を止めてはいけない、が製品オーナーの絶対条件）。

---

## 2週間後に見る数字

トライアル終了後、ログアプリのレコードから以下を集計する。

| 指標 | 定義 | 見方 |
|---|---|---|
| 総検索回数 | ログレコードの総数 | そもそも触られているか |
| 実稼働日数 | `searched_at` の日付のユニーク数 | 継続利用されているか（1日だけの検証で終わっていないか） |
| 開封率 | `clicked_at` が入っているレコード数 ÷ 総検索回数 | 検索結果を実際に確認しているか（「1件も開かなかった」検索の裏返し） |
| 1位採用率 | `clicked_rank = 1` のレコード数 ÷ `clicked_at` が入っているレコード数 | 1位表示の精度・信頼度 |
| 役立った率 | `feedback = '役に立った'` の数 ÷ `feedback ≠ '未回答'` の数 | 定性評価（母数が少ない場合は参考程度に） |
| 空振り検索の目視 | `result_count = 0` のレコードを一覧で目視 | 検索対象が足りていない/未登録図面が多い等の兆候 |

「開封率」が低い場合は結果表示自体の見せ方（サムネイル・スコア表示）を、
「1位採用率」が低い場合はスコアリングロジック側の見直しを優先する。
