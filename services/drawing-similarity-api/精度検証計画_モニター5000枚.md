# 精度検証計画：モニター企業 実図面5,000枚

最終更新: 2026-07-25（初版）

## 目的

モニター企業の実図面約5,000枚を検索対象として drawing-similarity の精度を検証し、LP に掲載できる「検証手続きを説明できる数字」を出す。

---

## 結論：LP に載せる数字の候補と優先順位

| 優先 | 指標 | LP 表現例 | 備考 |
|---|---|---|---|
| 主 | **Hit@10（Top10到達率）** | 「実図面5,000枚での検証で、類似図面の◯◯%を検索上位10件以内に表示」 | クエリ単位のサンプリングで成立し、一般の人にも説明しやすい |
| 主(数値次第) | Hit@3 / Hit@1 | 「◯◯%は上位3件以内」 | 数値が良ければこちらを前面に |
| 副 | 人手評価 Precision@5 | 「上位5件のうち◯◯%が『参考になる図面』（現場技術者判定）」 | 正解付けの負担が軽く、体感に近い |
| 副 | 業務効果 | 「図面探しの時間を平均◯分 → ◯秒」 | LP 的には最も刺さる。モニター企業へのヒアリング/実測が必要 |
| 社内用 | MRR・Recall@k・vectorRaw 分布 | （掲載しない） | チューニングと改善判断用 |

**Hit@k を主指標にする理由**：Recall 系は「全正解ペアの網羅」が前提で、5,000枚（約1,250万ペア）では正解の全数把握が不可能。Hit@k はクエリをサンプリングすれば成立し、「探したい図面が上位に出たか」という利用者の体感とも一致する。

---

## 本検証の核心：正解データ（ground truth）の作り方

5,000枚の全ペア評価は不可能なので、性質の異なる2系統で作る。

### A. メタデータ由来の自動正解（must-find ペア）

「見つかって当然」のペアを機械的に抽出する。ここでの Hit@k はベースラインとして高く出るべき値。

- 同一図番の改訂（rev）違い
- 図番の枝番・親子関係（例：`ABC-100-1` と `ABC-100-2`）
- 同一品名＋同一材質の family

抽出元は **kintone フィールドの人手入力値を優先**する。OCR 抽出値から正解を作ると、OCR を使う検索側と評価側が同じ誤りを共有する循環評価になるため。

目安：クエリ 100〜300 件。`pairs.json` 形式への変換スクリプトを新設する。

### B. 現場エンジニアによる正解付け（human-labeled）

- 層化サンプリングでクエリ図面 50〜100 枚を選定（形状カテゴリ・年代・図面サイズで層化し、偏りを避ける）
- モニター企業の担当者に「この図面と似ている・流用元になり得る図面」を挙げてもらう
- 探し方は自由（記憶・図番台帳など）。ただし**本システムで探させない**こと（評価の汚染防止）
- 担当者の工数が確保できない場合の軽量代替：本システムの top20 を提示して○×判定してもらう **precision 方式**に切り替える（楽だが「取りこぼし」は測れない点を認識しておく）

### 類似の定義（判定基準書）— 着手前にモニター企業と合意する

| Grade | 定義 | 集計上の扱い |
|---|---|---|
| 2 | 流用設計の元にできる（同形状で寸法・材質違い程度） | Hit@k の正解 |
| 1 | 参考になる（似た形状・似た加工） | 人手 Precision の「参考になる」 |
| 0 | 無関係 | 不正解 |

この基準書がないと判定者ごとにブレて、数字の説明責任が果たせなくなる。

## 実施ステップ

### Step 0：事前合意（Week 1）

- データ取扱の合意（NDA。当方が保持するのはベクトル＋検索用テキスト＋暗号化サムネイルのみ、という既存設計を明文化して提示）
- **LP 掲載の許諾**（社名掲載可否。「製造業A社」等の匿名表記の合意でも可）
- 判定基準書（上記 Grade 定義）の合意
- 成功基準のすり合わせ（例：Hit@10 ≥ 90% なら LP 掲載、未達なら改善後に再測定）

### Step 1：取込（Week 1、数日）

- 5,000枚を一括インデックス（バイナリ直送経路。数千件連続処理の OOM 対策は実装済み）または `/archive-index`
- **設定を固定して記録**：`EMBEDDING_PROVIDER`、`EMBED_IMAGE_MODE`、`EMBED_ROTATIONS`、スコア重み（`SCORE_*`）。検証途中で変えた場合は全再インデックス＋再評価
- 取込結果を記録：成功／失敗枚数。LP の「5,000枚」の裏付けとして、実際に検索対象化できた枚数を明記する

### Step 2：正解セット作成（Week 2〜3、A/B 並行）

- A：自動生成スクリプト → `eval/pairs.json` 形式へ
- B：判定用スプレッドシート（クエリ画像＋候補一覧）を用意して担当者に依頼

### Step 3：評価実行（Week 3）

- `eval/eval.js` を拡張（下記タスク参照）して実行
- 自動正解(A)と人手正解(B)は**別集計**する（性質が違う数字を混ぜない）
- `vectorRaw` 分布を確認し floor/ceiling を較正。較正は表示スコアのみで順位に影響しないが、**重み合成（vector/metadata/shape）は順位に影響する**ので、変更したら再測定

### Step 4：チューニングと最終測定 — リーク防止（Week 3〜4）

1. 正解セットを開発用（dev）と最終報告用（test）に分割（例：50/50）
2. dev で重み・`EMBED_IMAGE_MODE` 等をチューニング
3. 設定を凍結し、**test で1回だけ測定**した数字を LP に使う

これを省くと「チューニングに使ったデータで測った数字」になり、実運用で下振れして信頼を失う。

### Step 5：数字のまとめと LP 表現（Week 4）

- LP には**方法論の脚注を必ず付ける**：「製造業モニター企業1社の実図面◯枚を対象、クエリ◯件、現場技術者による正解判定、2026年◯月時点」
- 悪かった数字も含めて社内レポート化（改善ロードマップの材料）
- 補助数字も採取：検索応答時間、取込スループット、（可能なら）図面探し時間の削減効果ヒアリング

## リスクと対策

| リスク | 対策 |
|---|---|
| 図番等のフィールド不備で自動正解が作れない | kintone 人手入力値を優先。不足分は B（人手）比率を上げる |
| vectorRaw が高域に密集し順位が不安定（README 既知） | shape/metadata 重みで補正。根本改善は ROI 抽出の改善（表示スコアの較正では順位は変わらない） |
| 担当者の判定工数が確保できない | precision 方式（top20 の○×）を主にし、hit 方式はクエリ 30 件まで縮小 |
| 数字が目標未達 | LP は時間削減・Precision 系の表現に切替。Hit@k は改善後に掲載 |
| 類似図面が存在しないクエリが混入 | クエリ選定時に除外。別途「類似なしを正しく返せるか」の評価として分離してもよい |
| モニター企業が社名掲載 NG | 「製造業A社（従業員◯名）」等の匿名表記を Step 0 で合意しておく |

## スケジュール目安（約4週間）

```
Week 1 : 事前合意・判定基準書・5,000枚取込
Week 2-3: 正解セット作成（A自動 / B人手 並行）
Week 3 : 評価スクリプト拡張 → dev 測定 → チューニング
Week 4 : 設定凍結 → test 測定 → レポート・LP 文言確定
```
