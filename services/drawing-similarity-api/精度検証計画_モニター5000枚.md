# 精度検証計画：モニター企業 実図面5,000枚

最終更新: 2026-07-25（v2：正解セット方式をマルバツ判定ゲームに一本化）

## 目的

モニター企業の実図面約5,000枚を検索対象として drawing-similarity の精度を検証し、LP に掲載できる「検証手続きを説明できる数字」を出す。

## v2 での方針変更

- 当初案の「メタデータ（図番 family）由来の自動正解」は**不採用**。図番が似ていても同種の図面とは限らないため（モニター企業の図番体系の実情）
- 「担当者が5,000枚から類似図面を探して正解を挙げる」方式も**不採用**。工数的に破綻する
- 正解付けは**ブラインドの○×判定ゲームに一本化**。ルール・問数・判定基準は → **精度検証_マルバツ判定ルール.md**（確定済み）
- これに伴い主指標を Hit@k から **有用率@5・Precision@1** に変更（取りこぼし＝Recall 系は原理的に測れないことを認識した上での選択。将来プーリング方式で補完）

## LP に載せる数字の候補と優先順位

| 優先 | 指標 | LP 表現例 | 備考 |
|---|---|---|---|
| 主 | **有用率@5** | 「実図面5,000枚・無作為100クエリのブラインド判定で、上位5件以内に参考図面が見つかったケース◯◯%」 | 「見つかるか」の体感に一致。○×判定だけで測れる |
| 主 | **Precision@1** | 「検索1位の図面が『参考になる』と判定された割合◯◯%（ランダム提示では◯%）」 | ランダム対比とペアで訴求 |
| 副 | Precision@5 | 「上位5件のうち◯◯%が参考になる図面」 | |
| 副 | 業務効果 | 「図面探しの時間を平均◯分 → ◯秒」 | モニター企業へのヒアリング/実測が必要 |
| 社内用 | vectorRaw 分布・判定一致率 | （掲載しない。脚注の信頼性根拠には使う） | チューニングと品質管理用 |

## 実施ステップ

### Step 0：事前合意（Week 1）

- データ取扱の合意（NDA。当方が保持するのはベクトル＋検索用テキスト＋暗号化サムネイルのみ、という既存設計を明文化して提示）
- **LP 掲載の許諾**（社名掲載可否。「製造業A社」等の匿名表記の合意でも可）
- ○×判定ルールの説明と判定者のアサイン（主判定者1名＋副判定者1名推奨、合計60〜90分×人数）
- 成功基準のすり合わせ（例：有用率@5 ≥ 90% なら LP 掲載、未達なら改善後に再測定）

### Step 1：取込（Week 1、数日）

- 5,000枚を一括インデックス（バイナリ直送経路。数千件連続処理の OOM 対策は実装済み）または `/archive-index`
- **設定を固定して記録**：`EMBEDDING_PROVIDER`、`EMBED_IMAGE_MODE`、`EMBED_ROTATIONS`、スコア重み（`SCORE_*`）。検証途中で変えた場合は全再インデックス＋再測定
- 取込結果を記録：成功／失敗枚数。LP の「5,000枚」の裏付けとして、実際に検索対象化できた枚数を明記する

### Step 2：判定ツール準備（Week 2）

- 出題セット生成スクリプト（クエリ100件無作為抽出・上位5件＋ランダム1件・再出題5%・全問シャッフル。seed 記録）
- ○×判定ページ（1画面1ペア・キー操作・進捗保存・結果 JSON 出力。`/render-thumbnail` 流用）
- 集計スクリプト（Precision/有用率/一致率/95%信頼区間、CSV 出力）

### Step 3：判定実施（Week 2〜3）

- キャリブレーション10問（集計外）で基準を固定 → 本番約630問をセッション分割で実施
- 品質ゲート：再判定一致率90%未満なら定義を見直して再実施（詳細はルール文書）

### Step 4：チューニングと最終測定 — リーク防止（Week 3〜4）

1. クエリ100件を開発用（dev）50件と最終報告用（test）50件に分割
2. dev の判定結果で重み・`EMBED_IMAGE_MODE` 等をチューニング
3. 設定を凍結し、**test 側の数字だけを LP に使う**
   - 注意：検索設定を変えると上位5件の顔ぶれが変わるため、test 側は**凍結後の設定で出題セットを生成してから判定**する（dev 判定→チューニング→test 出題→test 判定、の順。判定を2ラウンドに分ける理由）
4. チューニング不要と判断した場合（初回設定のままで良い数字が出た場合）は分割せず100件全体を報告値にしてよい。その場合「チューニングなしの素の数字」であることを脚注に書けるので、むしろ訴求は強い

### Step 5：数字のまとめと LP 表現（Week 4）

- LP には**方法論の脚注を必ず付ける**：「製造業モニター企業1社の実図面◯枚、無作為◯クエリ、現場技術者によるブラインド○×判定、再判定一致率◯%、2026年◯月時点」
- 悪かった数字も含めて社内レポート化（改善ロードマップの材料）
- 補助数字も採取：検索応答時間、取込スループット、（可能なら）図面探し時間の削減効果ヒアリング

## リスクと対策

| リスク | 対策 |
|---|---|
| 判定者の工数が確保できない | 1セッション10〜15分×6回に分割済み。最悪、主判定者1名＋再出題チェックのみで成立 |
| 判定がブレて数字の信頼性が下がる | キャリブレーション10問・「迷ったら×」・再判定一致率の品質ゲート（ルール文書参照） |
| 類似図面が存在しないクエリが混入し数字が下がる | 除外しない（実運用の正直な数字にする）。ただし「アーカイブに類似が無いケース」の比率として脚注で説明できるよう、×のみクエリ数を記録 |
| vectorRaw が高域に密集し順位が不安定（README 既知） | shape/metadata 重みで補正。根本改善は ROI 抽出の改善（表示スコアの較正では順位は変わらない） |
| 数字が目標未達 | LP は時間削減系の表現に切替。精度数字は改善後に掲載 |
| モニター企業が社名掲載 NG | 「製造業A社（従業員◯名）」等の匿名表記を Step 0 で合意しておく |
